# MoneyBeetle 시스템 설계

## 개요

MoneyBeetle은 **Spring Boot MVC + Thymeleaf(서버가 화면을 만들어 응답) + MySQL** 구조로 설계합니다. 부트캠프에서 학습한 구조(Spring Web MVC · JPA · Spring Security 세션 로그인)를 그대로 따르고, 화면 안의 일부 동작(중복 확인, 알림 등)만 `/api/v1` JSON을 `fetch`로 호출합니다. 지금 페이지 구현본은 20개 화면이 각자 브라우저 localStorage에 목업 데이터를 저장하는 프로토타입이라, 이 저장과 판정을 모두 서버로 옮기고 화면은 Thymeleaf 템플릿으로 옮기는 것이 설계의 중심입니다.

**기준 자료**: 페이지 구현본(사용자 12·강사 4·관리자 4개 화면과 ROUTES.md의 향후 URL)을 기준으로 하고, 규칙은 요구사항 명세서와 정책 정의서를 따릅니다. 구현본과 문서가 다른 부분은 마지막 절에 모았습니다.

**기술 스택**: 서버·화면 방식은 팀 프로젝트 골격(`moneybeetle/build.gradle`)과 학습 내용으로 **확정**된 것이고, 캐시는 가정입니다. **배포는 하지 않고 로컬에서 발표**하며(팀 결정 2026-11-08), 파일도 로컬 폴더에 저장합니다.

| 영역 | 기술 | 근거 |
| --- | --- | --- |
| 화면 | Thymeleaf(서버 렌더링) + HTML·CSS·JavaScript(`static/`) | 확정. 학습 구조(Spring Web MVC + Thymeleaf). 페이지 구현본(`.dc.html`)을 템플릿으로 옮김 |
| 서버 | Java 21 + Spring Boot 3.5, Spring Web MVC, Spring Security, Spring Data JPA, Gradle | 확정 (`build.gradle`). 권한 필터·트랜잭션을 기본 제공 |
| DB | MySQL 8 | 확정. 캐시·거래·청약처럼 정합성이 중요한 데이터 |
| 캐시 | 서버 메모리(Caffeine) | 가정. 서버 한 대(로컬)라 Redis 는 쓰지 않음 |
| 파일 | 로컬 폴더 `./uploads` (`FileStorageService`, `file.upload-dir`) | 팀 결정 (2026-11-08). 배포하지 않아 오브젝트 스토리지는 쓰지 않음. 구현본에 강의 영상·썸네일·단지 이미지 업로드가 있음 (확인) |
| 배포 | **하지 않음** (로컬 발표). CI는 GitHub Actions 빌드·테스트만 (`.github/workflows/ci.yml`) | 팀 결정 (2026-11-08), #67 |

**설계 원칙**

1. **화면은 보여 주기만, 판정은 서버가**: 구현본은 레벨 해금·출석·가점·당첨을 브라우저에서 계산합니다. 실제 서비스에서는 모두 서버가 계산하고, 화면은 서버가 Model로 넘겨 준 결과만 보여 줍니다 (SP-24, SP-35, DP-14).
2. **돈은 한 번에 함께 바뀜**: 캐시·경험치·자산이 바뀌는 작업은 하나의 트랜잭션으로 묶고, 같은 활동으로 두 번 지급하지 않습니다 (DP-40, SP-18).
3. **설정값은 서버 한 곳에**: 구현본의 `mb-config.js`(레벨·칭호·해금·출석·청약 납입 값)는 서버 설정 테이블로 옮기고, 서버가 화면을 만들 때 Model로 넘겨 줍니다. 관리자가 바꾸면 서버를 다시 빌드하지 않아도 반영됩니다 (NFR-13).
4. **지난 것은 바뀜지 않음**: 지난 턴 가격, 체결된 거래, 지급 내역은 수정하지 않고 새 기록을 더하는 방식으로만 바꿉니다 (DP-41).

강조 색: 판정을 내리는 유일한 곳

이 프로젝트는 **배포하지 않고 발표용 노트북에서 로컬로 실행**합니다(팀 결정 2026-11-08). 브라우저의 모든 요청(화면 요청과 `/api` 요청)은 Spring Boot 서버로 바로 가고, 캐시·가점·당첨을 바꾸는 것은 이 서버뿐입니다. 서버가 화면(HTML)까지 만들어 응답합니다. 영상·이미지 같은 파일도 예외 없이 서버를 거쳐 올립니다. 서버가 형식·용량을 검사한 뒤 로컬 폴더(`./uploads`)에 UUID 이름으로 저장하고, DB에는 화면에서 쓸 주소(`/uploads/저장이름`)를 저장합니다. 보여 줄 때는 `WebConfig`가 `/uploads/**` 요청을 그 폴더와 연결해 서버가 파일을 직접 내려 줍니다.

| 구성 요소 | 배치 | 역할 |
| --- | --- | --- |
| 클라이언트 | 브라우저 (발표 노트북) | 서버가 만든 HTML을 보여 줌. 일부 동작만 `/api`를 `fetch`로 호출하고 브라우저에는 화면 편의 설정만 저장 |
| 웹 서버 | 발표 노트북 (`./gradlew bootRun` 또는 IntelliJ 실행) | 화면 렌더링(Thymeleaf), 인증·권한, 모든 업무 규칙, 메모리 캐시, 예약 작업(탈퇴 정보 정리, 만료 토큰 삭제), 업로드 파일 제공 |
| DB | 로컬 MySQL 8 (`money_beetle`) | 모든 업무 데이터와 감사 기록. `schema.sql` + `sample-data.sql`로 만든다 |
| 파일 | 로컬 폴더 `./uploads` | 영상·썸네일·프로필·단지 이미지. Git 에는 올리지 않음 (`.gitignore`) |
| 캐시 | 서버 메모리 | 오늘의 용어, 강의 목록, 현재 턴 시세, 설정값 (파일 업로드와 캐시 전략 절) |
| 외부 서비스 | 구글·카카오, 유튜브 | 간편 로그인(우선순위 하), URL로 등록한 강의 영상 재생 |

## 애플리케이션 모듈 구성

서버는 **도메인(기능 영역)별 패키지**로 나눕니다. 패키지 이름은 팀 프로젝트 골격(`moneybeetle/README.md`)을 따르고, 담당·이슈 범위는 `docs/MoneyBeetle_역할분담.md`와 GitHub 이슈의 담당자 배정을 기준으로 합니다. 같은 도메인 안에서도 이슈에 따라 담당자가 다를 수 있습니다. 모든 도메인 안은 `controller` / `model/dao` / `model/dto` / `model/entity` / `model/service` / `exception`으로 같은 모양입니다. 화면은 역할별 주소(`/user`, `/instructor`, `/admin`)로 나뉘고, 관리자·강사용 Controller·Service도 해당 도메인 안에 둡니다(`AdminCourseController` 등). 코드 작성 규칙은 코딩 컨벤션 문서를 따릅니다.

| --- | --- | --- | --- | --- |

**담당 구분 유의사항**: 위 표는 도메인의 기본 담당을 요약합니다. 파일 단위 담당은 `docs/MoneyBeetle_역할분담.md`의 이슈별 배정과 실제 GitHub 이슈 담당자를 따릅니다. `HomeController`는 홈 API(#13, DBA ②)와 검색 API(#15, PM)가 함께 있으므로 기능별로 구분합니다.

핵심은 `growth`입니다. 캐시·경험치를 바꾸는 코드는 `growth`(`RewardService`)에만 두고, 퀴즈·모의투자·청약은 그 지급·차감 메서드를 불러서만 값을 바꿉니다. 다른 도메인의 Repository는 직접 쓰지 않고 그 도메인의 Service 메서드를 부릅니다. 알림은 `notification.NotificationService`, 관리자 작업 기록은 `operation.AdminLogService`가 맡아서 각 모듈이 알림·기록 코드를 직접 만들지 않습니다.

## 핵심 처리 흐름

실수하면 캐시·자산이 어긋나는 네 가지 흐름을 서버 처리 순서로 정리했습니다. 네 흐름 모두 **검증 → 한 트랜잭션 안에서 변경 → 기록** 순서를 따릅니다.

**① 퀴즈 제출 → 학습 완료 → 보상** (QST-02~05, GRW-03~08)

1. 서버가 제출된 답을 채점합니다. 정답은 제출 전에 화면으로 보내지 않습니다 (SP-35).
2. 응시 기록을 저장하고 틀린 문제를 오답노트에 넣습니다 (이미 있는 문제는 건너뜀).
3. 70점 이상이고 이 강의를 처음 통과한 경우에만: 학습 완료 기록 → 경험치 지급 → 레벨 재계산(여러 레벨이면 레벨마다 캐시) → 학습 완료 캐시 → 새로 열린 기능 확인.
4. 1~3은 하나의 트랜잭션입니다. 하나라도 실패하면 모두 되돌립니다.
5. 응답으로 점수·해설·받은 보상·새로 열린 기능을 한 번에 돌려줍니다. 화면은 이 값으로 레벨업·해금 모달을 띄우고, 같은 요청 키로 다시 제출되면 서버는 처음 결과를 그대로 돌려줍니다.

**② 모의투자 다음 턴 진행** (ADM-14, INV-05, INV-12)

1. 관리자가 버튼을 누르면 서버가 다시 점검합니다: 휴장일이 아닌지, 다음 턴의 30개 종목 가격과 뉴스가 모두 있는지.
2. 시즌의 ‘현재 턴 번호’를 1 올리고, 턴 진행 기록(누가·언제)을 남깁니다. 되돌리기는 없습니다.
3. 주문에는 항상 ‘어느 턴 가격으로 주문했는지’가 담겨 옵니다. 현재 턴과 다르면 거절해서, 턴이 넘어가는 순간의 주문도 안전하게 막습니다.
4. 턴이 넘어가면 가격·뉴스 캐시를 비우고, 참가자의 평가금액은 조회할 때 계산합니다.

**③ 청약 공고 상태와 당첨 산정·발표** (ADM-36~39, SP-75)

1. 공고 상태는 구현본처럼 모집 예정 → 모집 중 → 모집 마감 → 발표 완료 네 단계입니다. 앞의 세 단계는 DB에 저장하지 않고, 서버 KST 시각과 공고 일정(게시 10:00, 마감 18:00)으로 그때그때 계산합니다. 그래야 상태를 바꾸는 예약 작업이 돌지 않아도 틀리지 않습니다.
2. 신청하면 그 순간의 가점·항목별 점수·납입회차·인정금액을 신청 기록에 함께 저장하고 접수번호를 발급합니다.
3. 발표일(서버 KST) 이후 관리자가 산정 버튼을 누르면, 저장된 가점 기준으로 당첨·예비 당첨·낙첨을 정해 한 트랜잭션으로 저장합니다(구현본의 `computed`). 추첨에 쓴 시드 값도 남깁니다.
4. 관리자가 발표 버튼을 눌러야 발표 완료가 되고 사용자에게 결과와 알림이 갑니다(구현본의 `announcedAt`). 산정과 공개를 나누어, 확인 전에 결과가 새어 나가지 않게 합니다.

**④ 청약통장 납입** (SUB-04, SUB-05)

1. 하루 1회만 허용합니다. ‘오늘 납입 기록이 있는지’는 회원 + 날짜 유니크 제약으로 DB가 막습니다.
2. 캐시 차감 → 통장 잔액 증가 → 인정금액 증가(1회 인정 상한까지만) → 납입회차 +1을 한 트랜잭션으로 처리합니다. 구현본 설정은 최소 2만·최대 50만, 인정 상한 25만입니다.
3. 납입 내역에는 납입액과 인정액을 따로 남깁니다. ‘40만 내었는데 인정은 25만’ 같은 문의에 내역으로 답할 수 있습니다.

모의투자 시즌 정산(ADM-32)도 ③과 같은 방식입니다. 최종 자산·이월금·랭킹을 한 트랜잭션으로 확정하고, 공개는 별도 버튼으로 합니다.

## 인증 및 보안 전략

인증은 학습한 **Spring Security 세션 로그인**을 씁니다. 서버가 화면과 `/api`를 같은 주소에서 내보내므로 CORS 설정이 필요 없고, 토큰을 브라우저 저장소에 두지 않아 스크립트로 훔칠 수 없습니다. JWT는 나중에 모바일 앱이 생기면 추가합니다. 로그인 요청(`POST`)은 Controller 메서드가 아니라 **Security 필터가 처리**하고, 우리는 회원 조회(`AuthService`)와 성공·실패 처리(`AuthSuccessHandler`·`AuthFailHandler`)를 끼워 넣습니다.

지금 구현본은 로그인하면 `localStorage`에 `mb-role`·`mb-admin-session`을 적고 이 값으로 화면을 보여 줍니다. 브라우저 개발자 도구로 값을 바꾸면 관리자 화면이 열리므로, 서버 연동 때 가장 먼저 없애야 할 부분입니다.

**인증 방식**

| 항목 | 방식 | 관련 규칙 |
| --- | --- | --- |
| 로그인 입구 | 사용자 `/login`, 강사 `/instructor/login`, 관리자 `/admin/login`으로 화면은 나뉘지만 로그인 처리는 Security 하나. 로그인 후 역할과 다른 입구로 들어오면 거절 | USR-06, USR-10 |
| 세션 쿠키 | 로그인 성공 시 세션 ID를 새로 발급(세션 고정 공격 방지). `HttpOnly`, `Secure`, `SameSite=Lax` | DP-11 |
| 내 정보 조회 | 서버가 화면을 만들 때 역할·레벨·캐시·설정값을 Model(또는 Thymeleaf Security 확장 `sec:authorize`)로 템플릿에 넘겨 사이드바와 잠금 표시에 씀. localStorage에 저장하지 않음 | HOM-04 |
| 세션 만료 | 30분 미활동 시 만료. 화면 요청은 로그인 화면으로 이동(302)하고 로그인 후 원래 주소로 돌아감, `/api` 요청은 401 | DP-11 |

| 강사 가입 | 강사 회원가입은 ‘승인 대기’ 상태로 만들고, 관리자가 승인해야 INSTRUCTOR 권한이 생김 (구현본 기준) | SP-07, ADM-06 |

| 비밀번호 저장 | BCrypt 해시. 평문 저장·로그 기록 금지 | DP-02 |
| 비밀번호 찾기 | 일회용 토큰을 만들고 해시만 DB에 저장. 10분 유효, 한 번 쓰면 폐기. 구현본은 ‘준비 중’ | DP-12 |

**권한 (인가)**

- 역할은 `MEMBER`, `INSTRUCTOR`, `ADMIN`을 회원 테이블에 둡니다. 강사는 승인 상태(대기·승인·반려)도 함께 가집니다.
- 주소 단위로 막습니다(`SecurityConfig`): `/admin/**`·`/api/v1/admin/**`는 ADMIN, `/instructor/**`·`/api/v1/instructor/**`는 승인된 INSTRUCTOR, 모의투자·모의 청약은 로그인 + 레벨 조건(`@RequireLevel`). 권한 규칙은 위에서부터 검사하므로 좁은 규칙을 앞에 둡니다.
- 화면의 블러·잠금 표시는 편의 기능일 뿐입니다. 레벨 해금은 서비스에서 DB 값으로 매번 확인합니다 (SP-24, NFR-09).
- 본인 데이터(오답노트·캐시·거래·청약 내역)는 주소에 회원 ID를 받지 않고 세션의 회원 ID로만 조회합니다 (NFR-03).
- 비공개 문의글과 강의 Q&A는 ‘작성자 또는 그 강의의 강사 또는 관리자’일 때만 내용을 돌려줍니다 (SP-40).

## 파일 업로드와 캐시 전략

**파일 업로드**: 구현본에는 여섯 종류의 업로드가 있습니다. 배포하지 않고 로컬에서 발표하므로(팀 결정 2026-11-08), 파일은 서버 실행 폴더의 `./uploads`(yaml `file.upload-dir`)에 UUID 이름으로 저장하고 DB에는 화면에서 쓸 주소(`/uploads/저장이름`)를 저장합니다. 아래 표의 "스토리지"는 이 로컬 폴더를 뜻합니다.

| 파일 | 올리는 화면 | 업로드 방식 | 제한 |
| --- | --- | --- | --- |
| 강의 영상 | InstructorCourseCreate | 영상마다 한 번씩 `POST /api/v1/instructor/courses/{courseId}/lessons/video`(파일 하나)로 올리면 서버(`@RequestParam MultipartFile`, 형식·용량 검사) → `FileStorageService` → 스토리지에 저장하고 `videoUrl`을 돌려준다. 강의 저장(`PUT .../lessons`, API 78)은 각 영상의 `sortOrder`(순서)·`title`·`videoUrl`·`durationSeconds`(재생 시간)·`summary`(요약글)를 담은 `lessons` 배열을 한 번에 보낸다. 이미 저장된 영상을 고칠 때만 `lessonId`를 함께 넣고, **새 영상은 `lessonId`를 생략**한다(서버가 새로 만들어 응답의 `lessonIds`로 돌려준다). 요청 예시는 API명세서 78번. 파일 업로드로 확정(#31). **구현 필요(운영 스토리지)**: 지금 `FileStorageService`는 로컬 폴더(`file.upload-dir`)에 저장하고 `/uploads/…` 주소를 돌려주는 구현뿐이다. 운영 환경에서는 영상이 오브젝트 스토리지에 저장되도록 스토리지 저장 구현(`FILE_STORAGE_TYPE=s3`, 환경변수 문서)을 추가해야 하고, 로컬 구현을 그대로 운영에 연결하지 않는다 | 강의당 3개, 영상 1개 500MB 이하 mp4 (DP-33, 확정). 한 요청에 파일 하나만 담아 요청 한도 510MB를 넘지 않는다 |
| 강의 썸네일 | InstructorCourseCreate | 브라우저 → 서버(형식·용량 검사) → 스토리지 | 이미지, 용량 미정 |
| 프로필 이미지 | UserMyPage | 위와 같음 | 2MB, jpg·png (DP-32) |
| 청약 단지 이미지 | AdminHousingManagement | 위와 같음 | 이미지, 용량 미정 |
| 퀴즈 문항 파일 | InstructorCourseCreate (csv·xlsx 등) | 서버가 바로 읽어 문항으로 바꾸고 파일은 저장하지 않음. 한 행이라도 틀리면 전체 취소하고 오류 행 표시 | 문항 수 규칙 (DP-34) |
| 종목 가격 CSV | AdminTradingManagement | 위와 같음 | ADM-21 |

영상은 크기가 커서 저장·전송 비용이 큽니다. 파일 업로드로 받되 영상 1개 500MB 이하로 제한하고(확정), 서버의 multipart 한도(`max-file-size` 500MB)와 `FileStorageService`의 용도별 검사(이미지 2MB, 영상 500MB)를 함께 둡니다. 영상·이미지는 `FileStorageService.saveImage()`·`saveVideo()`가 확장자와 파일 내용(매직 넘버)으로 형식을 확인합니다. 검수 중인 강의의 영상을 다른 사람이 보지 못하게 하는 것은 화면·API 권한(강의 상태)으로 막습니다.

저장·조회는 로컬 폴더 하나만 씁니다. `FileStorageService`가 `./uploads`에 저장하고, `WebConfig`가 `/uploads/**` 주소를 그 폴더와 연결해 서버가 파일을 직접 내려 줍니다. 배포하지 않으므로(팀 결정 2026-11-08) 오브젝트 스토리지·서명 주소는 구현하지 않습니다.

**캐시**: 많이 읽고 거의 안 바뀌는 것만 캐시합니다. 캐시·자산처럼 정확해야 하는 값은 캐시하지 않고 항상 DB에서 읽습니다.

| 대상 | 캐시 기간 | 비우는 시점 |
| --- | --- | --- |
| 오늘의 경제 용어 5개 | 그날 자정(KST)까지 | 관리자가 오늘 세트를 바꿀 때 |
| 카테고리·소주제·공개 강의 목록 | 10분 | 강의 허가·비공개, 카테고리 수정 때 |
| 현재 턴의 종목 가격·뉴스 | 턴이 바뀔 때까지 | 다음 턴 진행 때 |
| 공개된 시즌 랭킹 | 시즌 종료 후 고정 | 랭킹 공개 때 한 번 생성 |
| 운영 설정값(지급액·해금 레벨 등) | 10분 | 관리자가 설정을 저장할 때 |

로컬 서버 한 대로 발표하므로 서버 메모리 캐시(Caffeine)로 충분합니다. 캐시 인터페이스(Spring Cache)를 쓰면 나중에 저장소를 바꿔도 코드를 거의 바꾸지 않아도 됩니다.

## 인프라 및 배포환경

> 📌 **팀 결정 (2026-11-08)**: 이 프로젝트는 **배포하지 않고 로컬에서 발표**합니다. Docker·Nginx·클라우드 서버·자동 배포는 만들지 않고, CI는 **GitHub Actions 빌드·테스트만** 둡니다(`.github/workflows/ci.yml`, #67).

발표 노트북에서 MySQL과 Spring Boot 서버를 직접 실행하고 브라우저로 `http://localhost:8080`에 접속합니다. 코드는 PR마다 GitHub Actions가 빌드·테스트로 확인하고, 시연·제출 시점에 `dev`를 `main`으로 합칩니다(Git 규칙).

```mermaid
flowchart LR
    PR["PR 올리기<br/>기능 브랜치 → dev"] --> CI["CI 검사 (GitHub Actions)<br/>JDK 21 · ./gradlew build<br/>DB 없이 테스트"]
    CI -- 실패하면 고쳐서 다시 push --> PR
    CI --> M["dev 병합<br/>리뷰 1명 승인 후"] --> MAIN["main 병합<br/>시연·제출 시점 (dev → main)"]
    MAIN --> RUN["발표 노트북에서 실행<br/>MySQL + ./gradlew bootRun"]
    style RUN fill:#E6F1FB,stroke:#378ADD,stroke-width:2px
```

**발표 노트북 준비 순서**

1. MySQL 8 에서 `create_database.sql` → `schema.sql` → `sample-data.sql` 순서로 실행한다 (`moneybeetle/README.md`).
2. `moneybeetle/.env.example`을 `moneybeetle/.env`로 복사해 DB 계정을 넣는다 (환경변수 문서).
3. `main`을 받아 `moneybeetle/`에서 `./gradlew bootRun`(또는 IntelliJ)으로 서버를 띄우고 `http://localhost:8080`에 접속한다.
4. 시연에 쓸 업로드 파일은 미리 올려 `./uploads`에 둔다 (Git 에 올라가지 않으므로 발표 노트북에서 직접 올린다).

저장소(github.com/bukkeu/my-home-finish)는 `moneybeetle/`(Spring Boot 프로젝트: 서버 코드, `templates/`, `static/`), `docs/`(설계 문서), `moneybeetle-page/`(페이지 구현본, 참고용)로 나뉩니다. 구현본의 `.dc.html` 화면은 ROUTES.md의 향후 URL대로 `templates/` 아래 Thymeleaf 템플릿으로 옮기고, 공통 스크립트(`mb-*.js`)와 CSS는 `static/`으로 옮깁니다.

**환경 구분**

| 환경 | 어디서 | DB·파일 | 용도 |
| --- | --- | --- | --- |
| local | 각자 노트북 (개발) · 발표 노트북 (시연) | 로컬 MySQL 8, 로컬 폴더 `./uploads` | 개발과 발표. `sample-data.sql` 시드로 시연 데이터 준비 |
| CI | GitHub Actions (ubuntu) | DB 없음 | PR·병합 때 빌드·테스트만 |

dev·prod 서버 환경은 두지 않습니다 (배포하지 않음, 팀 결정 2026-11-08).

**환경설정**

- 설정 파일은 `application.yaml` 하나만 둡니다. 환경이 로컬 하나뿐이라 `application-{local,dev,prod}.yml`로 나누지 않습니다.
- DB 주소·비밀번호, OAuth 키는 파일에 적지 않고 `moneybeetle/.env`(Git 제외)나 IntelliJ 실행 설정의 환경변수로 넣습니다. `.env.example`만 저장소에 올립니다. CI는 DB 없이 테스트하므로 GitHub Secrets가 필요 없습니다.
- 서버·DB 시간대는 모두 `Asia/Seoul`로 맞춥니다 (DP-42).
- DB 구조 변경은 DBA가 `schema.sql`에 반영하고, 이미 DB를 만든 팀원을 위해 `sql/migration/<날짜>_<설명>.sql`을 함께 남깁니다 (`moneybeetle/README.md`).
- 화면은 서버가 렌더링하므로 별도의 프런트 빌드·환경변수·프록시가 없습니다. `static/`과 `templates/` 파일은 Spring Boot 서버에 함께 들어갑니다.

## 로깅·모니터링·에러 처리

오류는 서버가 `BusinessException` + 도메인별 `ErrorCode`로 던지고, `GlobalExceptionHandler`가 **요청 종류에 따라** 바꿔 돌려줍니다. 화면 요청은 에러 화면(`templates/error/403·404·500.html`)이나 입력 폼의 안내 문구로, `/api` 요청은 `ApiResponse` JSON(`success`·`data`·`error`, API 명세서 1-2)으로 응답합니다. 정책서의 에러 문구는 서버가 코드와 함께 내려주어 화면마다 문구가 달라지지 않게 합니다.

```json
{ "success": false, "data": null, "error": { "code": "NOT_ENOUGH_CASH", "message": "캐시가 부족해요", "fields": null } }
```

| 오류 종류 (EP-01) | HTTP 상태 | 화면 표현 (EP-06) |
| --- | --- | --- |
| 입력 오류 (글자 수, 형식) | 400, `error.fields`에 입력칸 이름 (`@Valid` 실패 메시지) | 입력칸 아래 문구 |
| 로그인 필요·세션 만료 | 화면 302(로그인 화면), `/api` 401 | 로그인 화면으로, 로그인 후 원래 화면 |
| 권한 없음·레벨 미달 | 403 (레벨이면 필요 레벨 포함) | 잠금 모달 또는 공통 오류 페이지 |
| 규칙 위반 (캐시 부족, 신청 기간 밖, 휴장일) | 409 / 422 | 토스트 또는 모달로 이유와 다음 행동 |
| 없는 데이터 | 404 | 공통 오류 페이지 + 홈 버튼 |
| 서버 오류 | 500 | “처리하지 못했어요. 내 정보는 바뀌지 않았어요” (EP-03) |
- **로그**: 요청마다 요청 ID를 붙여 시각·회원 ID·주소·결과·원인을 JSON 한 줄로 남깁니다. 비밀번호·세션 ID·토큰은 로그에서 가립니다 (EP-05, DP-02). 구현(#84): `RequestLogFilter`가 요청 ID(응답 헤더 `X-Request-Id`)·회원 ID를 MDC에 넣고 요청마다 "메서드 경로 상태 시간" 한 줄을 남긴다. 경로만 남기고 쿼리·경로 매개변수(`;jsessionid=` 등)·본문·파라미터 값은 쓰지 않는다. JSON 파일은 `local` 프로필의 `logs/moneybeetle.log`(10MB마다 나눔, 7일 보관).
- **감사 기록과 구분**: 애플리케이션 로그는 일정 기간(7일) 뒤 지우고, 관리자 작업 감사 기록은 DB에 계속 보관합니다.
- **모니터링**: 배포하지 않으므로 외부 생존 확인·알림은 두지 않습니다. Spring Boot Actuator의 상태 확인 주소(`/actuator/health`)는 발표 전 로컬 점검에 씁니다 (#84). `health`·`info`만 열고 세부 정보는 숨기며, DB가 끊기면 DOWN, 메일 도구는 확인에서 뺍니다.
- **운영 점검 화면**: 관리자 대시보드에 ‘다음 턴 가격·뉴스 비어 있음’, ‘발표일이 지났는데 산정 안 된 공고’ 같은 경고를 보여 줍니다. 사람이 버튼을 눌러야 하는 작업을 놓치지 않기 위해서입니다 (ADM-08, ADM-14).
